## Functionality

- Upload one valid file of each format (PDF, DOCX, TXT) and confirm each opens intact afterward.
- Try unsupported formats (DOC, RTF, ODT, XLSX, PNG, ZIP) and check for a clear rejection message.
- Test files at the size limit: 19.99MB, exactly 20MB, 20MB + 1 byte, and 0 bytes. Check whether "20MB" means 20,000,000 or 20,971,520 bytes.
- Use uppercase or mixed-case extensions (.PDF, .Docx) and double extensions (report.pdf.txt).
- Use filenames with spaces, Unicode or Thai characters, emoji, very long names, and reserved names (CON, NUL).
- Check the progress indicator on slow or throttled networks, with tiny files (does it flash or skip?), and when it reaches 100% but the server fails.
- Cancel mid-upload, drop the network mid-upload, close the tab, and refresh. Check for orphaned partial files and whether progress resets correctly.
- Run concurrent uploads, upload the same file twice (duplicate handling), and upload two files with the same name.
- Check behaviour when the session expires during a long upload.

## Data Integrity

- Compare checksums (SHA-256) of the original and the downloaded copy for every format.
- Check that DOCX metadata, tracked changes, comments and embedded images are preserved.
- Test TXT encodings: UTF-8, UTF-8 with BOM, UTF-16, Windows-1252, and line endings (CRLF/LF).
- Upload a PDF with form fields, digital signatures, or multiple pages, and confirm nothing is altered or flattened.
- Check that a failed or partial upload never leaves a corrupt document visible as "successful."
- Confirm the audit record matches reality: one entry per attempt, the correct user, timestamp (time zone), filename, size and outcome.
- Test failure paths (virus scan fail, storage full, DB down) and check that an audit entry is still written, marked as failed.
- Check audit behaviour under concurrency: no lost or duplicated entries for simultaneous uploads.

## Security

- Check access control: another user, an admin, or an unauthenticated user tries to access the document by URL or ID (IDOR, guessable or sequential IDs).
- Check whether the document appears in other users' search results, listings, thumbnails or previews.
- Spoof the file type: an EXE renamed to .pdf, a mismatched Content-Type header, or a polyglot file. Verify the server checks magic bytes, not just the extension.
- Upload malicious content: a PDF with embedded JavaScript, a DOCX with macros or external entity references (XXE), or a zip-bomb DOCX.
- Try path traversal in filenames (../../etc/passwd) and XSS payloads in filenames shown in the UI or audit log.
- Bypass the size limit on the client and send larger files directly to the API. Confirm the server enforces the 20MB cap.
- Confirm uploads use HTTPS only and files are encrypted at rest. Check that direct storage links (e.g. S3) aren't public or long-lived.
- Check whether audit records can be modified or deleted by ordinary users.
- Check whether audit logs leak sensitive data, such as document contents or tokens.
- Test for denial of service: rapid repeated uploads, many parallel 20MB uploads, and whether rate limiting is in place.
- Test CSRF on the upload endpoint, and check that uploads are rejected without a valid auth token.

**Clarifying questions for the team:** Is virus scanning in scope? What counts as a "report" in the audit (fields, retention)? Can the uploader later share the document, and is that covered by a separate story?
